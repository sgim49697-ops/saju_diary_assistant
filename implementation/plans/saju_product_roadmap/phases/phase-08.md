# Phase 8. 앱 오차단 수정·S3 지시문 비교

## 목적과 현재 상태

상태: **8A 후보 구현·CPU 확인 완료 / 8B 실행 준비**. 8A는 v1.17 앱 후보, 8B는 S3/50-B2 실험이다. v1.16의 기존 CPU 25개는 그대로 보존하며 새 후보 45개 CPU·6개 합성 브라우저 검사는 별도 [실행 기록](../../../history/2026-09-16-phase8-intent-s3.md#phase8a)으로 연결한다. 실제 모델 확인이나 운영 배포 완료를 뜻하지 않는다. [로드맵](../README.md)·[50](../50-automatic-model-evaluation.md)·[실험 상세](../../saju_system_context_diagnosis.md)를 따른다.

## 진입 조건

Phase 7 완료와 해당 작업의 별도 실행 범위를 확인한다. 앱 코드는 v1.16을 부모로 별도 후보에 두고, S3는 동결된 S2 입력·R16·검사 버전을 재구성한다. 앱 변경을 S3에 혼입하지 않는다. 두 작업이 같은 파일/index를 동시에 수정하지 않도록 소유권을 나눈다.

## 작업 순서

<a id="error-boundary"></a>
### 최초 오류 위치 분리

모델 호출 전 오차단은 앱, 최신 facts 누락은 상태·전달, 사주 역할·장문 지시 충돌은 S3, 정상 입력 활용 실패는 S3/S4/S5, 부정·인용 오판은 검사기, 학습 분포 문제는 S5로 분류한다. S0~S2를 반복하지 않고 새 후보 때문에 달라진 조건만 점검한다. 실제 모델 오류와 검사기 누락·오탐을 구분하고 큰 모델로 호출 전 차단을 해결하려 하지 않는다.

<a id="routing"></a>
### 8A: 날짜 표현과 운세 의도 분리

| 개발 회귀 입력 | 기대 처리 |
|---|---|
| 오늘 야근했어 | 일반 공감, 날짜 검사 없음 |
| 어제 영화 보고 왔어 | 일반 대화, 날짜 검사 없음 |
| 내일 면접이라 긴장돼 | 공감·면접 준비, 날짜 검사 없음 |
| 이번 주에 운동 시작했어 | 일반 대화, 날짜 검사 없음 |
| 내일 점심은 뭘 먹지? | 일반 대화, 날짜 검사 없음 |
| 사주 말고 그냥 들어줘 | 사주 제외 일반 대화 |
| 내일 운세를 봐줘 | 활성 날짜 운세 요청, 날짜 검사 |
| 사주 말고 내일 운세를 알려줘 | 남은 별도 운세 요청, 날짜 검사 |
| 오늘은 힘들었어. 내일 운세는 어때? | 일상 절과 운세 절 분리, 내일만 계산 요청 날짜로 검사 |
| 그럼 내일은 어때? — 이전 사주 대화 | 기존 맥락에서 날짜 운세 후속임이 명확하면 날짜 검사 |
| 그럼 내일은 어때? — 이전 일반 대화 | 면접·식사 등 명확한 일반 주제의 후속; 날짜 검사 없음 |
| 그럼 내일은 어때? — 맥락 없음·불명확 | 최소 의도 확인; 임의로 운세/일반 대화로 확정하지 않음 |

현재 v1.16 함수에서 첫 네 문장을 period_request로 분류하는 것을 로컬 분리 호출로 재현했다. 이는 live 서비스 전체 실행 결과가 아니다. snapshot 날짜가 우연히 같아 통과해도 잘못된 의도 분류는 실패다.

날짜·흐름·해석 단어 하나로 운세를 확정하지 않는다. 제외된 주제와 별도 능동 요청을 구분하고, 날짜 추출은 활성 계산 요청 절에만 적용한다. 모호함을 모두 운세로 차단하거나 모두 일반 대화로 통과시키지 않는다. 일반 단어 정규식 목록을 끝없이 늘리거나 모든 요청에 확인을 요구하는 방식으로 종료 기준을 맞추지 않는다. 전달된 snapshot은 의도와 관계없이 무결성을 검증한다. 계산값·기존 세션·S3 입력은 유지한다.

8A는 오차단 수정만 담당한다. 모호한 후속의 의도 판별에 필요한 기존 맥락은 읽기 전용으로 참조할 수 있지만 이력 재작성·snapshot 전환·모델 컨텍스트 재구성은 하지 않는다. 해당 변경은 [Phase 10](phase-10.md#revision-history)에서 기존 계약 안의 최소 후보로 다룬다. 위 세 맥락 회귀는 같은 현재 문장을 사용하며 판별 과정에서 기존 이력·binding·모델 입력이 변경되지 않는지도 확인한다.

<a id="s3-controls"></a>
### 8B: S3 통제

질문은 같은 R16·같은 승인 사실에서 지시문만으로 현재 요청 수행이 개선되는가다. 현재 R16 가중치/adapter, C_FULL JSON·직렬화, 48개 대상 turn·동결 부모 이력, tokenizer/template·정밀도·생성 설정·상한·종료·동일 새 진단 검사 버전을 고정한다. 시스템 지시문만 바꾼다. 각 arm 자신의 응답을 다음 이력으로 사용하는 자유 대화는 별도 관찰이며 비교에 섞지 않는다. 프로그램 직접 조회나 재시도 교정으로 모델 성공을 대신하지 않는다. 상한은 48×2=96요청이다.

<a id="instruction-bundle"></a>
### 최종 지시문 묶음 하나

P0 파일은 보존한다. P1은 별도 후보 하나로 원문·hash를 동결한다. bound_chart_v2 파일뿐 아니라 `_runtime_model_context_from_binding()`이 추가하는 원국·일진 지시까지 최종 입력에서 확인한다. 두 위치를 바꾸면 하나의 지시문 묶음 변경으로 선언하고 변경 구간·token 차이를 기록한다. 개별 문장 하나의 효과로 과장하지 않는다.

P1은 승인 fact·권한·range/unknown 유지, 현재 작업·형식 우선, 일반 대화에서 불필요한 사주·출생 재질문 방지, 잘못된 전제·이전 오답보다 최신 snapshot 우선, 명시적 짧은 요청보다 최소 세 문장 권고를 우선하지 않기, 무관한 사실·반복 사과·정형 안내 강제 제거를 담는다. 질문별 정답·기대 fact 목록을 추가하지 않는다.

<a id="experiment-vs-product"></a>
### 동결 기대값과 제품 계약 구분

S3의 case별 필수 사실은 유지한다. 날짜 질문에 원국·날짜 각각 한 사실을 요구하는 계약과 단순 일진 조회가 충돌하면 사전 점검의 한계로 기록하고 사후 완화하지 않는다. 제품의 불필요한 원국 삽입 완화는 [Phase 10](phase-10.md#response-contract)에서 새 계약으로 양쪽 후보에 동일 적용한다.

## 입력·산출물

8A는 원문 10개(모호한 후속 하나는 세 맥락으로 나눔)와 최소 표현 변형·기존 25개 회귀, 의도/확인/차단의 기대 상태와 별도 앱 후보를 남긴다. 8B는 동결 P0/P1 묶음·config·실행 신원·입력 차이·요청별 trace·공개 aggregate/manifest/verification을 남긴다. 실제 CLI와 버전은 해당 구현에서 확정하며 과거 runner 명령을 그대로 새 실험 명령으로 안내하지 않는다.

## 검증

CPU에서 일반 대화·명시 요청·혼합 날짜·제외·후속 문맥·tampered/stale binding·범위 밖·불필요 확인을 검사한다. 8B의 비지시 텍스트·JSON·이력 동일성과 예산을 확인한 뒤 유휴 GPU·고정 환경·native JIT 조건에서 순차 실행한다. 공통 [평가 규칙](phase-12.md#evaluation-common)과 [예산](phase-07.md#budget)을 따른다. 앱 지표와 모델 원응답 지표는 분리한다.

<a id="s3-exit"></a>
## 종료·중단과 다음 단계

8A는 사전 정의한 오차단·안전 회귀를 닫으면 후보 확인을 종료한다. 8B는 항목별 개선·회귀·불변·판정 불가·한계를 기록하면 종료한다. 모두 정답이나 P1 채택은 필수가 아니다. 같은 48개를 보며 P2/P3를 추가하지 않는다. 8B 뒤 [Phase 9](phase-09.md)를 진행하며 8A나 전체 모드 구현 때문에 S4를 미루지 않는다. 실행 부적격·예산 초과는 원인을 남기고 추가 시도를 자동 수행하지 않는다.

## 원문 대응

모델 문서 §3~4, 전체 문서 §4와 CPU 체크리스트 중 날짜 의도를 반영한다. [원문·섹션 색인](../source-20260915.md)과 [행별 반영표](../requirements-20260915.json)를 따른다.

- 2026-09-16 S3 준비: 전용 `scripts.evaluation.system_context_s3`와 P1 지시문 묶음 하나를 구현했다. 48개 P0 부모 입력/비지시 영역 일치, 96요청/10사전 차단, 최대 입력 1,692 token의 dry-run과 CPU 18개를 통과했다. 아직 실제 생성·S3 완료는 아니며 [고정 구성·CLI·권한](../../../history/2026-09-16-phase8-intent-s3.md#phase8b)을 따른다.

- 2026-09-15 보완: 8A의 맥락 읽기 전용 경계와 동일 후속 문장의 세 맥락 회귀를 계획에 명시했다. 실제 의도 코드·이력·snapshot·모델 입력과 8B 실행은 변경하지 않았다.

- 2026-09-15: Phase 7에서 계획만 등록했다. 네 일반 문장의 기존 의도 분류만 읽기 전용으로 재현했으며 새 앱 구현·S3 생성·배포는 미실행이다.
