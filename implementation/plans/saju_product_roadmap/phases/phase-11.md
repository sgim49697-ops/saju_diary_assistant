# Phase 11. S5 데이터·학습 필요성 가설과 조건부 명세

## 목적과 현재 상태

상태: **완료 — S5 기존 데이터 전수 대조·학습 가설·조건부 명세만 작성**. `build-27a91a8e21a8`에서 실제 R16 입력 2,000행·기존 개발 200행·teacher 이력·보정 상태·학습 manifest와 S3/S4 집계를 CPU로 대조하고 재검증했다. [완료 기록](../../../history/2026-09-17-phase11-data-hypotheses.md#phase11)을 따른다. [50-D](../50-automatic-model-evaluation.md)·[60 데이터](../60-mix20k-v3-1-build.md)·[70 학습](../70-training-and-promotion.md)의 판단 자료이며 데이터 추가·400건 재개·학습 실행은 확정하지 않는다. 다음은 Phase 12의 후보 전체 구성 동결·실제 확인이며 새 24문항은 아직 만들거나 사용하지 않았다.

## 진입 조건

S3/S4 결과·앱 후보의 변경 목록·남은 오류 위치를 확보한다. S4 미실행은 숨기지 않으며 전체 진단 완료로 표시하지 않는다. 현재 R16의 실제 2K build와 별도 보정의 출처·권한을 확인한다.

## 작업 순서

<a id="data-baseline"></a>
### 데이터 단서와 한계

일반 공감 250건은 원국 미연결, 최종 답변 1,751/2,000건은 세 줄 이상, 짧은 사실 QA 축은 50건이다. 다른 축에 유사 행동이 전혀 없다고 단정하지 않지만 공감 전용 축이 연결 상태 일반 전환을 직접 대표하지는 않는다. 줄 수와 문장 수를 혼동하지 않는다.

최종 2K는 Codex 초안 2,000건·Claude 최종 판정 191건·Codex 분리 판정 1,809건의 승인 fallback이다. 전량 교차-provider 판정이라고 표현하지 않고 같은 provider의 분리 판정이라는 이유만으로 무효화하지도 않는다. 자연스러운 축약·올바른 제한 문구가 정규식에 걸려 재작성된 이력을 점검한다. 최종 데이터 전체 결함의 증거는 아니지만 좋은 요청 수행보다 검사 문법에 맞는 답이 선택됐을 가능성을 검토한다.

전수 재집계에서 위 수량을 확인했다. 공감 250행은 모두 단일 턴이고, 후속 설명 300행은 모두 원국 연결·이전 assistant 한 턴을 가진다. 원문 계약의 최소 비공백 3줄은 1,700행·1줄은 300행이다. 두 문장·한 단어·사주 제외·틀린 전제 확인의 지정 문자열은 0건이지만 정규식 범위 밖 의미 커버리지는 미측정이다. 최종 답변의 exact duplicate 초과 행은 0, 정규화 동일 답변 최대 반복은 2, template family는 102개다.

실제 teacher state의 재작성은 0회 1,857행·1회 111행·2회 32행이다. 결정적 초안 검사 실패 75회 중 `CLAIM_GRAMMAR` 73회·미분류 2회, 자동 판정 시도는 PASS 2,187·FAIL 116회다. 시도 수를 학습 행 수와 혼동하지 않는다. 검사 문법·길이 조건의 편향 가능성은 남지만 실패 코드만으로 73회를 오탐이라 부르거나 기존 accepted 응답을 변경하지 않는다. 자기 보고 `used_fact_paths`는 의미 정확성의 증명이 아니다.

학습 당시 token/mask/EOS 감사 2,000/2,000행을 정확히 재현했고 동일 대화를 학습/serving tokenizer로 처리한 token ID·mask도 전량 같았다. 최대 rendered 1,960·prompt 1,802·supervised assistant 169 token, 학습 상한 2,048, truncation·user/system loss 누출·마지막 EOS 비감독은 모두 0이다. 이는 직렬화·mask 결함의 근거가 없다는 뜻이지 모델의 컨텍스트 활용 능력이나 최신 제품 입력의 동등성을 증명하지 않는다. 최신 후보의 정보 선택은 과거 full snapshot과 의도적으로 다르며 system 전체 원문 hash 차이도 포함 facts 차이와 template 차이를 구분해야 한다.

기존 비봉인 개발 200행의 **정규화 마지막 질문은 학습 질문과 200/200행 겹쳤다**. 전체 부모 대화·chart fingerprint 일치는 각각 0행이며 개발 자료에는 template family metadata가 없다. 질문 틀의 중복이지 전체 샘플 중복·정답 유출의 증명은 아니다. 기존 split을 수정하지 않고 새 언어 표현 일반화 근거로 사용하지 않는다. 의미상 계열 중복은 미측정이며 Phase 12 질문·부모·seed 계열 분리를 다시 확인한다.

<a id="repair-decision"></a>
### 400건 유지·재설계·보류 제안

기존 accepted 238·판정 대기 3·초안/재작성 159와 원본 state를 보존한다. 현재 R16에 미반영이며 다른 세션 결과를 취소하지 않는다.

| 선택 | 조건과 조치 |
|---|---|
| 유지 | 보정 축이 남은 주요 오류와 일치; 계약·자동 판정 적합성 확인 후 별도 재개 |
| 재설계 | 연결 일반 대화·형식 전환 등 핵심 분포 부족; 이전 결과 보존·새 범위/build |
| 보류 | 앱/지시로 주요 오류 해소 또는 효과 근거 부족; 생성·학습하지 않음 |

무조건 2K에 400을 더해 2,400건으로 만들지 않는다. builder가 교체·보정·결합 중 무엇인지 확인하고 최종 행 수를 새 manifest에서 확정하도록 조건부 명세에 적는다. 위 선택은 제안이며 재개 승인이 아니다. [Phase 12](phase-12.md#training-decision)의 실제 제품 후보 결과를 대조한 뒤에만 [Phase 13](phase-13.md)의 실행 여부를 별도 결정한다.

현재 제안은 **보류**다. 읽기 전용으로 확인한 `repair-23340fc31022`는 accepted 238·needs_review 3·needs_draft 159, provider 호출 55회다. 실제 계약은 intake 250·uncertainty 100·짧은 QA 50행을 **교체**하고 1,600행을 계승해 최종 2,000행을 만드는 구조다. 현재 R16에는 미반영이다. 연결 일반 대화·주제 전환을 직접 보정하는 구성이 아니므로 400건을 완료하면 전체 문제가 해소된다고 가정하지 않는다. Phase 12에서 필요한 축이 남으면 기존 state를 보존한 새 범위/build로 재설계하고, 필요성이 반증되면 재개하지 않는다.

<a id="failure-attribution"></a>
### 학습 선택과 최소 변경

모델 전 차단·잘못된 전달은 먼저 앱/상태를 수정한다. 기존 진단과 데이터 분포를 근거로 정상 입력의 잔여 모델 오류·표적 데이터 필요성 가설을 작성하고 Phase 12에서 대조할 반증 조건을 명시한다. 지시문으로 해결된 축에는 데이터 확대를 요구하지 않는다. R16은 비교 기준이지 자동 최종 승자가 아니다. 20K Full FT 재실행·rank 전수 탐색·3B 학습을 묶지 않는다. 여러 변수를 바꿔야 하면 묶음 개선임을 기록한다.

조건부 명세는 다음과 같으며 `execution_authorized=false`다. Phase 12 뒤 필요성이 확인돼도 별도 실행 계약·예산·승인이 없으면 실행하지 않는다.

| 항목 | 조건부 명세 |
|---|---|
| 출발점·방식 | 고정 K0 `kakaocorp/kanana-2-1.3b-instruct@bf4786aa2a1908adce942d53976270132732f720`에서 새 LoRA r=16·alpha=32; KI20/R16 이어학습 아님 |
| 데이터·행 수 | 실패로 확인된 행동만 교체하는 잠정 2,000행; 1,600+400은 기존 builder 계약 설명이며 새 보정 범위·최종 행 수는 새 manifest로 확정 |
| split | 질문/부모/seed 계열을 분리한 학습·개발; 기존 dev 200의 질문 중복 한계 보존. 소비한 Phase 12 질문은 학습·학습 후 새 확인에 재사용 금지 |
| 길이·loss | 선호 상한 2,048, assistant-only, packing=false. 새 전체 token/mask/EOS·잘림 0 검증 후 길이 확정; 과거 768·최소 3줄 계약 자동 계승 금지 |

| 중단·재개 | 비유한 loss/gradient·입력/mask/split 불일치·자원 Gate 위반 시 중단. 동일 입력·설정·코드·checkpoint identity만 재개 |
| 검증·건너뜀 | 새 데이터 비학습 감사→단일 학습→별도 새 질문/자동 회귀. 앱·지시문으로 목표 오류가 해소됐으면 명세·400건 존재와 무관하게 학습 건너뜀 |

## 입력·산출물

응답별 오류 분류·S3/S4 결과·후보 입력 계약·고정 데이터/학습 manifest를 입력으로 삼는다. 산출물은 유지/재설계/보류 제안, 이유·반증 조건, 학습 필요성 가설·보정 대상·조건부 학습 명세다. 명세에는 출발 checkpoint·방식·rank·행 수·split·길이·학습률·epoch·예산·중단/재개·새 검증 범위를 적되 실행 확정으로 표시하지 않는다.
