# Phase 12. S6 새 질문·실제 후보 앱 확인

## 목적과 현재 상태

상태: 미실행. 새 합성 24개는 아직 만들거나 사용하지 않았다. CPU 모의 경로와 실제 모델·worker·브라우저 확인을 구분한다. 이 문서의 공통 평가 원칙은 Phase 8/9부터 적용하며 Phase 12 실행을 기다리라는 의존 관계가 아니다.

## 진입 조건

S3/S4 결과·S5 결정, 후보 하나·P1/정보 정책/검사·제품 계약을 동결한다. S4 미실행을 완료로 치환하지 않는다. 실제 통합 확인의 요청 범위·예산·기준 경로와 후보 경로를 사전에 정한다.

## 작업 순서

<a id="evaluation-common"></a>
### 세 층의 자동 평가

1. 계산·상태: 고정 입력의 facts·불확실성·revision·무결성. 운세 해석의 정답률 아님.
2. 모델 단독: 같은 질문·사실·부모 이력의 원응답. 프로그램이 채운 값·재시도 교정 답을 모델 성공으로 세지 않음. S3/S4에서 고정.
3. 실제 앱: 요청→입력→worker→저장/API→화면의 수행 결과. CPU 모의 성공을 live 성공으로 바꾸지 않음.

| 지표 | 판정과 한계 |
|---|---|
| 현재 사실·필수 fact | 현재 주장한 값/역할과 case 요구; 정답 문자열 포함만으로 통과 금지 |
| 요청 수행 | 일반 전환·짧은 답·문장 수·재작성; 사실 하나 말한 것이 과제 성공은 아님 |
| 현재 상태 | 정정 전 원국·이전 오답보다 최신 snapshot; 과거 인용 구분 |
| 미지원 추론·권한 | 없는 관계·신강약·용신·사건 생성, 범위 우회 방지 |
| 일반 대화 오차단 | 생성이 없었다는 이유만으로 안전 성공으로 처리하지 않음 |
| 불필요 확인 | 명확한 요청까지 확인으로 보내 오차단을 줄이는 편법 방지 |
| 실행 안정성 | 입력 잘림·종료·출력 상한 도달·예상 밖 오류 |
| 출력 일치 | 원응답/저장/API/화면 차이와 사유 |
| 자원 | 동일 조건 지연·메모리, 로딩/생성·cold/warm 구분 |

PASS / FAIL / UNSCORABLE와 적용 가능 수·생성 수·판정 가능 수, 전체 조건표와 공통 판정 가능한 paired 결과를 함께 보고한다. 어려운 문장을 분모에서 빼거나 판정 불가 증가를 개선으로 포장하지 않는다. 자연스러움·해석 의미는 자동 계약이 없으면 not_measured다. 계약 밖 평가를 완료 조건으로 추가하지 않는다.

계산 권한·개인정보·상태 무결성 회귀 후보는 제외한다. 그 외는 사전 고정 선택 규칙을 따르며 우열 충돌을 임의 가중 평균으로 덮지 않는다. 미채택도 정상 결과다. 문법 오탐 수정은 원문·기존 점수를 보존한 새 버전으로 모든 해당 조건에 동일 적용하고 유리한 응답만 고치지 않는다. 단순 구조 검증을 전체 의미 품질 승인으로 부르지 않는다.

<a id="confirmation"></a>
### 새 합성 24개

8개 층×3개, 질문 변형·부모 대화·출생 seed 계열로 개발 48개/20문장·학습 자료와 분리한다. 개발 예시의 표면 표현만 바꿔 새 확인으로 쓰지 않는다. 후보·P1·projection·검사 기준을 고정한 뒤 한 번 사용하고 이 결과로 다시 조정해 같은 묶음에서 향상을 주장하지 않는다. 소비된 sealed blind는 열거나 재사용하지 않으며 새 질문도 학습 자료로 재사용하지 않는다.

기준은 R16/P0/C_FULL과 선택 후보 하나의 24×2=48요청이다. R16/P1과 3B/P0 결과만으로 미시험 3B/P1이나 새 projection이 이미 개선됐다고 가정하지 않는다. 새 조합이면 통합 후보임을 밝히고 선택 이유·평가 범위를 고정한다. S6가 첫 실제 확인이면 그 한계를 기록한다. 이 작은 합성 확인은 전체 사용자 정확도·장기 대화 품질 인증이 아니다. 나중에 데이터·학습이 달라지면 이미 소비한 S6를 새 평가로 재사용하지 않는다.

<a id="actual-app"></a>
### 실제 후보 경로와 요청 대조

같은 합성 요청에서 후보 worker·실제 loader·tokenizer·adapter·최종 입력·원응답·저장·화면까지 추적한다. 원국→일상/문장 작성→사주 복귀, 정정/날짜 변경·unknown/range·범위 밖·변조·새 세션/동시 요청을 확인한다. CPU 회귀와 실제 모델·브라우저 실행 수는 별도 기록한다.

앱 요청은 모델 생성, 프로그램 직접 응답, 확인 요청, 예상 차단, 예상 밖 차단/실행 오류, 미실행으로 전량 대조한다. 검증된 재사용은 별도로 표시한다. 직접 응답으로 GPU 비용이 줄어도 모델 추론 능력 향상은 아니다. 별도 앱 CPU 회귀는 새 GPU 요청이 아니며 추가 통합 생성이 필요하면 [예산](phase-07.md#budget) 밖으로 숨기지 않고 먼저 별도 등록한다.

## 입력·산출물

동결된 후보·기준선·새 합성 질문·기대값·실행 신원을 입력으로 한다. 산출물은 요청별 결과와 비공개 trace, 공개 집계·manifest·검증, 세 층의 비교·한계·후보 선정/미채택 사유다. 원시 출생·답변·키는 공개하지 않는다.

## 검증

계열 중복·재사용 identity·48요청 대조, 계산·privacy·상태 회귀, 원출력과 API/저장/화면 일치, 실제 실행 여부와 동일 측정 조건을 확인한다. 상한 도달·미실행을 성공으로 치환하지 않는다. 후보를 좋게 보이게 하려고 기존 기대값을 완화하지 않는다.

## 종료·중단과 다음 단계

실제 비교·제한·선택 또는 미채택 사유로 종료한다. 모든 미래 품질의 증명은 요구하지 않는다. 실행하지 못한 경로는 미실행으로 남긴다. 필요한 경우 별도 [Phase 13](phase-13.md), 아니면 확인된 후보에 한해 [Phase 14](phase-14.md)의 운영 결정을 검토한다. 진단·후보 확인·운영 전환은 별개다.
