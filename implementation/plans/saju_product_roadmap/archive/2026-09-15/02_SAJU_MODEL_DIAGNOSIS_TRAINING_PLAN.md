# 사주 모델 원인 진단·데이터·학습 계획

> **결정 제안:** 현재 계산기와 완료된 학습 결과를 보존한 채 S3 지시문 비교와 S4 실제 큰 모델 비교를 끝낸다. 그 결과로 입력·데이터·모델 규모 중 무엇을 바꿀지 결정한다. 데이터 추가나 재학습을 기본 다음 단계로 두지 않는다.

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-09-15, Asia/Seoul |
| 기준 저장소·커밋 | `sgim49697-ops/saju_diary_assistant` · `390ca88f4b65f6c3b87f0f36ca26cbc492251a06` |
| 문서 상태 | 기존 S3~S6의 실행·판단을 구체화하는 제안. 실험은 미실행 |
| 담당 범위 | 모델 입력, 지시문, 규모 비교, 데이터 커버리지, 학습 조건, 자동 평가 |
| 제외 범위 | 계산기 재구현, 날짜 오차단을 모델 학습으로 해결, 자동 운영 교체 |
| 관련 계획 | [계산기 계획](01_SAJU_CALCULATOR_SCOPE_PLAN.md), [전체 실행계획](03_SAJU_OVERALL_EXECUTION_PLAN.md) |

기존 모델·보고서·소비된 sealed blind는 보존한다. 이 문서 작성으로 모델 다운로드, GPU 생성, teacher 호출, 데이터 보정, 학습을 실행하지 않았다. 사람·전문가 판정을 새 완료 조건으로 추가하지 않는다.

## 1. 모델에게 맡길 일

모델의 역할은 계산 결과를 만드는 것이 아니라 현재 요청을 이해하고, 승인된 사실을 필요한 만큼 사용하며, 한국어 설명·공감·문장 작성을 수행하는 것이다.

목표 행동은 다음과 같다.

- 원국과 일진, 일주와 일간의 역할을 혼동하지 않는다.
- 사용자가 잘못된 전제를 말하면 현재 승인 사실에 근거해 교정한다.
- 원국이 연결돼 있어도 일반 대화 요청에는 사주를 강요하지 않는다.
- 짧은 답·문장 수·재작성 등 현재 요청의 형식을 따른다.
- 정정 전 사실이나 앞선 오답보다 현재 상태를 따른다.
- 시간 미상과 미지원 계산을 확정 사실로 바꾸지 않는다.

단순 필드 조회의 결정적 출력과 모델의 설명 생성은 제품 경로에서 분리할 수 있다. 다만 S3·S4 모델 진단에서는 기존 생성 경로를 유지하며, 프로그램이 대신 낸 정답을 모델 개선으로 계산하지 않는다.

## 2. 현재 기준선과 해석의 한계

### 2.1 모델·데이터 상태

| 항목 | 확인된 기록 | 판단 시 주의점 |
|---|---|---|
| K0 | 추가 사주 학습 전 Kanana-2 1.3B Instruct | 이름의 “기본”은 사전학습 Base checkpoint가 아닌 추가 학습 전 Instruct를 뜻함 |
| R8·R16·R32 | 동일 2K로 각각 LoRA 1 epoch·250 step 완료 | rank 증가가 기본 모델 크기 증가를 뜻하지 않음 |
| 현재 R16 | `build-54836f556b4f`, 학습 길이 2,048 | 별도 400건 보정 미반영 |
| KI20 | 20K Full FT 완료, 학습 길이 768 | R16과 데이터·방식·길이가 동시에 달라 단일 원인 비교가 아님 |
| 400건 보정 | accepted 238, 판정 대기 3, 초안·재작성 대기 159 | 완료한 400건이나 현재 학습 입력으로 취급하지 않음 |
| Phase 6 | `AUTOMATED_REPAIR_REQUIRED`로 단회 완료 | 평가 절차 완료와 제품 품질 승인을 구분 |

기준선은 [M1], 실제 학습·데이터 이력은 [M4][M5][M6]을 따른다. 기존 20K, 비학습 MIX20K-v3 후보, 실제 R16의 2K를 같은 데이터 버전으로 묶지 않는다.

### 2.2 최근 진단에서 알 수 있는 것

재채점된 필수 사실 지표의 적용 대상은 조건별 24문항이다. 표의 순서는 통과 / 실패 / 판정 불가다. [M3]

| 모델 | C_FULL | C_MIN |
|---|---:|---:|
| K0 | 3 / 20 / 1 | 2 / 20 / 2 |
| R16 | 11 / 6 / 7 | 6 / 10 / 8 |
| KI20 | 0 / 19 / 5 | 1 / 19 / 4 |

이는 전체 사주 정확도나 자연스러움 점수가 아니다. R16을 다음 비교의 기준으로 삼을 이유는 있지만, 실사용 모델로 승인할 수준이라는 뜻은 아니다. 판정 불가를 제외한 비율로 모델 순위를 만들지 않는다.

S2의 최대 입력은 1,692토큰, 이력 삭제는 0이었다. 전체·최소 정보 조건 모두에서 48개 입력 중 44개가 KI20 학습 길이 768을 넘었다. 입력이 잘리지 않았다는 사실은 정보 간섭이 없다는 증거가 아니며, 학습 길이 768은 추론에서 그 뒤를 읽지 못한다는 뜻도 아니다. [M6]

### 2.3 현재 결과로 확정하지 않을 결론

- “LoRA가 Full FT보다 본질적으로 좋다.”
- “작은 모델이라서 모든 오류가 생긴다.”
- “컨텍스트를 줄이면 반드시 좋아진다.”
- “검사기 문제를 고쳤으므로 모델 문제가 해결됐다.”
- “학습 loss가 낮거나 저장·재로딩이 일치하므로 사용 품질이 좋다.”

각 결론은 현재 통제된 비교와 측정 범위를 넘어선다.

## 3. 실험보다 먼저 구분할 문제

| 문제 위치 | 대표 증상 | 담당 작업 |
|---|---|---|
| 앱 라우팅 | 날짜 포함 일반 대화가 모델 호출 전에 차단 | 전체 계획의 앱 오차단 수정 |
| 상태·전달 | 최신 원국이나 필요한 필드가 모델 입력에 없음 | binding·revision·context builder 점검 |
| 지시문 | 일반 대화·짧은 요청보다 사주 설명 역할이 우선됨 | S3 |
| 모델 활용 | 올바른 입력을 받았지만 사실·요청을 잘못 사용 | S3·S4·S5 |
| 검사기 | 올바른 부정·인용·교정 표현을 오답으로 처리 | 기존 검사 범위 명시, 필요한 별도 버전 검증 |
| 학습 분포 | 연결 상태 일반 대화·정정·짧은 요청에 취약 | S5 데이터 점검과 조건부 보정 |

이미 완료된 S0~S2를 처음부터 반복하지 않는다. 새 모델이나 후보의 실행 조건 때문에 달라진 부분만 확인한다. 앱 오차단 수정은 병행할 수 있지만 동결된 S3·S4 진단 경로에 몰래 반영하지 않는다.

## 4. S3: 지시문 후보 하나 비교

### 4.1 비교 목적과 상한

질문은 “같은 R16과 같은 승인 사실에서 지시문을 바꾸면 현재 요청 수행이 개선되는가?”다.

| 항목 | 고정 또는 변경 |
|---|---|
| 모델 | 현재 R16 가중치·adapter 고정 |
| 정보 | 기존 C_FULL snapshot과 직렬화 형식 고정 |
| 질문·부모 이력 | 기존 48개 평가 대상 turn과 동결 부모 이력 고정 |
| 추론 | tokenizer/template, 정밀도, 생성 설정, 길이 상한, 종료 방식 고정 |
| 검사 | 동일한 새 진단 검사 버전 고정 |
| 변경 변수 | P0 대비 P1 지시문 정책 하나 |
| 요청 상한 | 48 × 2 = 96요청. 성공 응답 96개를 보장하는 수치가 아님 |

기존 계획의 순서와 상한을 유지한다. 첫 turn과 고정 부모 이력의 후속 turn을 같은 조건으로 비교한다. 각 arm이 새로 만든 답변을 다음 이력에 넣는 자유 대화는 별도 end-to-end 관찰이며 단일 지시문 효과와 섞지 않는다. [M2][M7]

### 4.2 지시문 파일이 아니라 최종 입력 전체를 확인한다

현재 사주용 지시는 두 곳에 있다.

1. `configs/chat_prompts/saju_bound_chart_v2.txt`.
2. 대시보드의 `_runtime_model_context_from_binding()`이 덧붙이는 원국·일진 사용 안내.

P1을 만들 때 두 위치의 최종 지시를 함께 확인한다. 텍스트 파일만 바꾸고 formatter의 충돌 지시가 그대로 남는 경우를 피한다. [M8][M9]

두 위치의 지시를 함께 바꾼다면 이를 하나의 **지시문 묶음 변경**으로 사전 정의한다. JSON 사실·메시지 역할·부모 이력은 유지하고 지시 텍스트의 변경 구간만 기록한다. 결과를 특정 문장 하나의 효과로 과장하지 않는다.

### 4.3 P1이 구현할 원칙

- 승인된 계산 사실과 미지원·불확실성 경계는 유지한다.
- 사용자가 지금 요구한 작업과 형식을 분명하게 우선한다.
- 일반 대화에서 사주 언급과 출생정보 재질문을 불필요하게 하지 않는다.
- 틀린 전제나 이전 답변보다 현재 승인 snapshot을 우선한다.
- 최소 세 문장 권고가 명시적인 짧은 형식 요청을 압도하지 않게 한다.
- 질문과 무관한 사실 설명·반복 사과·정형 안내를 요구하지 않는다.

실제 P1 원문과 hash는 실행 전에 하나만 동결한다. 질문별 정답이나 기대 fact 목록을 몰래 지시문에 추가하지 않는다.

### 4.4 기존 평가 계약과 제품 개선을 구분한다

“날짜 질문에는 원국 사실과 날짜 사실을 반드시 각각 하나 포함” 같은 기존 의무와 “일진만 알려줘”라는 요청이 충돌할 수 있다. S3 결과를 좋게 만들기 위해 해당 문항의 기대값을 사후 완화하지 않는다.

S3에서는 동결된 case별 사실 요구를 유지한 상태로 P0/P1을 비교한다. 사전 점검에서 계약 충돌이 발견되면 그 한계를 표시하고 기존 판정은 보존한다. 단순 QA의 원국 강제 삽입을 없애는 등 제품 응답 계약을 바꾸는 작업은 전체 계획의 별도 개선으로 다룬다. 새 계약으로 평가할 때는 두 후보 모두에 같은 기준을 적용한다.

### 4.5 종료 조건

항목별 개선·회귀·불변·판정 불가와 원인을 기록하면 S3는 종료한다. P1이 모든 질문을 맞혀야 끝나는 단계가 아니다. 유리한 결과가 없더라도 S4로 넘어간다. 같은 질문을 보면서 P2·P3를 계속 추가하지 않는다.

## 5. S4: 실제 큰 기본 모델과 비교

### 5.1 모델 후보와 비교 의미

첫 큰 모델 후보는 `kakaocorp/kanana-2-3b-instruct`로 제안한다. 공식 모델 카드에서 같은 Kanana-2 SLM 계열의 공개 모델임을 확인했다. 정확한 다운로드 revision과 가중치 hash는 아직 이 프로젝트 실행 후보로 등록하지 않았다. [E1]

공식 설명상 1.3B는 3B에서 가지치기·증류를 거쳐 나온 계열이다. 따라서 비교는 실용적인 규모·모델 구성 차이를 보는 것이며 순수 파라미터 수 하나만의 인과 실험은 아니다. 이 프로젝트에서 새로 가지치기를 하자는 제안도 아니다. [E2]

“3B”라는 모델명만으로 정확한 메모리 사용량을 계산하지 않는다. 실제 checkpoint 구성·정밀도·KV cache·런타임의 사용량을 preflight에서 측정한다. 큰 모델 진단은 작은 로컬 모델 목표를 포기하거나 3B 운영 전환을 미리 확정하는 결정이 아니다.

### 5.2 2×2 비교

| arm | 추가 사주 학습 | 지시 | 정보 |
|---|---|---|---|
| K0-FULL | 없음 | P0 | C_FULL |
| K0-MIN | 없음 | P0 | C_MIN |
| 3B-FULL | 없음 | P0 | C_FULL |
| 3B-MIN | 없음 | P0 | C_MIN |

상한은 48 × 2모델 × 2정보 조건 = 192요청이다. 기존 계획에 따라 **공통 P0**를 쓴다. S3 결과를 보고 모델별로 유리한 지시문을 골라 넣지 않는다. R16과 큰 기본 모델의 차이만으로 규모 효과를 판단하지 않는다. [M2][M7]

모델마다 공식 tokenizer와 chat template를 사용하고 revision을 기록한다. 의미상 같은 사용자 질문·사실·지시를 제공하되 서로 다른 모델의 token ID나 token 수가 동일할 필요는 없다. 잘림 없이 입력되는지는 각각 확인한다.

### 5.3 실행 전 최소 점검

| 점검 | 기록할 내용 |
|---|---|
| 모델 신원 | 정확한 모델 ID·revision·config·weight·tokenizer/template hash |
| 공식 배포 조건 | 라이선스 이름·파일, 필요한 loader와 custom code 여부 |
| 환경 | 현재 실행환경, GPU 종류·실제 여유 VRAM, 다른 작업과의 충돌 |
| 추론 조건 | dtype, adapter 유무, offload, KV cache, 입력·출력 상한, 종료 token |
| 실행 가능성 | 가장 긴 입력에서 정상 생성·종료, 메모리 부족·입력 삭제 없음 |
| 재사용 조건 | 과거 응답의 전체 실행 신원이 동일할 때만 검증 후 재사용 |

공식 카드의 라이선스 표기는 KananaOpenLicense다. 라이선스 확인은 후보 등록 정보이며 모든 사용 방식이 자동 허용된다는 법적 결론은 아니다. 모델을 읽기 위해 기존 환경 전체를 최신 버전으로 일괄 교체하지 않는다. 필요한 환경 변화는 분리한다. [E1]

동일 정밀도로 순차 실행하는 것을 원칙으로 한다. 메모리 부족을 이유로 한쪽만 양자화·CPU offload하거나 다른 모델로 자동 대체하지 않는다. 실행 불가 조건을 기록하고 대안을 별도 결정한다. 프리플라이트도 기존 요청 예산에 포함하며, 더 필요한 예산을 본 비교에 숨기지 않는다.

### 5.4 비교 결과의 해석

| 관찰 | 해석과 다음 선택 |
|---|---|
| 3B가 FULL/MIN 모두에서 일관되게 개선 | 모델 규모·구성 변경의 효과 후보. 비용과 작은 모델 역할 축소를 함께 검토 |
| 3B는 FULL에서만 뚜렷하게 개선 | 정보 선택·간섭에 대한 민감도 차이 가능성 |
| 두 모델 모두 MIN에서 개선 | 입력 선택 정책의 개선 가능성. 사실 손실 없는지 확인 |
| 두 모델 모두 같은 항목에 실패 | 지시·기대값·상태·검사·태스크 정의부터 다시 확인 |
| 3B는 일부만 개선하고 다른 축이 악화 | 임의 종합점수로 승자를 만들지 않음. 용도와 미측정 범위를 기록 |
| 자원 조건 때문에 3B 미실행 | `not_executed`와 필요 조건을 남김. 필수 크기 비교 완료로 표시하지 않음 |

3B가 더 잘하더라도 바로 재학습하지 않는다. 먼저 추가 학습 없는 후보의 효과를 확인하는 것이 이 단계의 목적이다.

## 6. S5: 실패 행동에 맞춘 데이터 보정 결정

### 6.1 지금 확인된 데이터 단서

현재 2K의 공감 전용 250건은 모두 원국 미연결 조건이다. 최종 답변 중 1,751건이 세 줄 이상이며, 짧은 사실 QA 축은 50건이다. 다른 축에 유사 행동이 전혀 없다고 단정할 수는 없지만 실제 제품의 “원국 연결 상태에서 일반 대화로 전환”을 공감 전용 축이 직접 대표하지는 않는다. [M5]

최종 2K는 실제 Codex 초안 2,000건, Claude 최종 판정 191건, Codex 분리 판정 1,809건의 승인된 fallback이다. 모두 교차-provider 판정을 받은 데이터라고 표현하지 않는다. 같은 provider의 분리 판정만으로 데이터가 무효라는 결론도 내리지 않는다. [M4]

과거 데이터 제작에서는 자연스러운 사실 축약이나 올바른 제한 문구가 정규식에 걸려 여러 차례 재작성됐다. 최종 데이터 전체가 잘못됐다는 증거는 아니지만, 사용자에게 좋은 답보다 검사 문법에 잘 맞는 답이 선택됐을 가능성을 점검한다. [M4]

### 6.2 먼저 보완 여부를 판단할 행동 축

| 행동 축 | 구성할 대조 | 기대 행동 |
|---|---|---|
| 연결 상태 일반 대화 | 동일 일상 질문 + 원국 연결/미연결 | 사주를 강요하지 않고 요청 수행 |
| 대화 전환 | 사주 설명 이후 “지금은 그냥 들어줘” | 연결 상태는 유지하되 응답 주제를 전환 |
| 짧은 형식 | 같은 사실에 한 단어/두 문장/자세한 설명 요청 | 요청에 맞는 길이·형식 |
| 틀린 전제 | 현재 사실과 충돌하는 사용자의 주장 | 동조하지 않고 현재 사실로 교정 |
| 정정·이력 | 이전 오답 또는 이전 원국 + 최신 snapshot | 현재 사실 우선, 과거 인용과 구분 |
| 필요한 사실 선택 | 답에 필요한 값만 변경 / 무관한 값만 변경 | 필요한 값 변화에는 반응, 무관한 변화에는 핵심 유지 |
| 불확실성 | 생시 미상·범위·미지원 기능 | 확정값·지원하지 않는 계산 생성 금지 |

이 표의 예시는 개발용이다. 표현을 약간 바꿔 S6의 독립 확인 질문으로 재사용하지 않는다.

### 6.3 400건의 처리

기존 accepted 238건과 미완료 상태는 보존한다. 완료하지 않은 400건을 현재 R16에 반영됐다고 표시하지 않는다.

S3·S4와 오류 분류 결과에 따라 다음 중 하나를 선택한다.

| 선택 | 선택 조건 | 처리 |
|---|---|---|
| 유지 | 기존 보정 축이 남은 주요 오류와 실제로 일치 | 현재 계약과 검수 방식의 적합성을 확인한 뒤 별도 재개 |
| 재설계 | 연결 상태 일반 대화·형식 전환 등 핵심 분포가 부족 | 기존 결과 보존, 새 범위와 build를 정의 |
| 보류 | 지시·앱 개선으로 주요 오류가 해소되거나 효과 근거 부족 | 추가 생성·학습을 하지 않음 |

400건을 기존 2K에 무조건 덧붙여 2,400건으로 학습한다고 가정하지 않는다. 해당 작업이 교체·보정·결합 중 무엇인지 실제 builder 계약으로 확인하고 새 최종 manifest에서 행 수를 확정한다.

### 6.4 새 데이터 제작 원칙

- 학습 입력과 실제 사용할 입력 구조를 맞춘다. 앱이 아직 쓰지 않는 축약형 JSON만 학습하지 않는다.
- 모든 답변에 세 줄·세 문장을 강제하지 않는다. 단순 사실 QA에는 짧은 정답이 자연스럽게 포함돼야 한다.
- 값의 단순 포함보다 역할·정정·부정·인용을 구분한다. 검사 문법 밖의 올바른 표현을 자동 오답으로 몰지 않는다.
- self-reported `used_fact_paths` 같은 표시는 보조 근거일 뿐, 실제 답변이 맞다는 증거를 대신하지 못한다.
- 정확한 fact·질문·부모 대화·변형 계열을 함께 관리해 split 간 중복을 막는다.
- 승인받은 teacher 범위와 합성 사실만 사용하고, 출생 원문·private 응답·키를 외부로 반출하지 않는다.
- provider가 다른지와 판정 호출이 분리됐는지를 구분해 기록한다. 독립 검수가 있었던 것처럼 포장하지 않는다.

## 7. 재학습을 선택하는 조건과 첫 실험

### 7.1 재학습 전 조건

정상적인 입력에서 같은 오류 유형이 남고, 이를 겨냥한 데이터가 실제 사용 계약과 맞을 때만 학습을 선택한다. 정상 요청이 모델 전에 차단되거나 필요한 사실이 전달되지 않는 상태를 먼저 학습으로 보정하지 않는다.

현재 R16이 일부 사실 사용에서 기준선 역할을 할 수 있으므로 새 보정도 소규모 단일 후보부터 비교한다. Full FT 20K 재실행, rank 전수 탐색, 3B 학습을 한 번에 묶지 않는다.

### 7.2 첫 학습에서 통제할 것

| 항목 | 원칙 |
|---|---|
| 출발점 | K0에서 새 adapter 학습인지 R16 이어학습인지 먼저 하나를 정함 |
| 데이터 | 변경 축과 최종 행 수·split·계열 중복·실제 입력 형식 기록 |
| 방식 | 선택 이유를 기록한 단일 LoRA 또는 학습 후보. 자동 Full FT 전환 없음 |
| 길이 | 학습 전체 입력·출력을 렌더링해 잘림 없이 수용. 작업명으로 장문 학습을 주장하지 않음 |
| loss | assistant-only mask, 사용자·시스템 누출, 종료 token 확인 |
| 파라미터 | 비교하지 않는 rank·학습률·epoch·template·정밀도는 고정 |
| 검증 | 저장·재로딩과 답변 평가를 분리. loss만으로 후보 선택 금지 |

데이터 효과를 보려는 실험에서 출발 모델·학습률·길이·rank를 동시에 바꾸지 않는다. 여러 변경이 필요한 경우 하나의 묶음 개선임을 밝히고 개별 원인의 효과로 해석하지 않는다.

## 8. 자동 평가와 후보 선택

### 8.1 지표를 분리한다

| 지표 | 평가 대상 |
|---|---|
| 사실 정확성 | 답변에서 현재 사실로 주장한 값과 역할 |
| 필수 사실 사용 | 해당 질문의 동결된 요구 사실을 사용했는가 |
| 요청 수행 | 일반 대화 전환·문장 수·재작성·짧은 답 등 측정 가능한 계약 |
| 현재 상태 유지 | 정정 전 사실·앞선 오답보다 현재 snapshot을 따르는가 |
| 미지원 추론 | 제공하지 않은 관계·신강약·용신·사건을 만들어내는가 |
| 실행 안정성 | 종료 사유, 입력 잘림, 출력 상한 도달, 오류 |
| 자원 | 동일 측정 조건의 지연·메모리와 cold/warm 여부 |

자연스러움과 해석 의미가 자동 계약으로 측정되지 않았다면 `not_measured`로 남긴다. 사람 평가를 새 필수 조건으로 추가하지 않으며, 측정하지 않은 품질이 승인됐다고 말하지도 않는다.

### 8.2 판정 불가와 회귀 처리

`PASS / FAIL / UNSCORABLE`를 구분하고 적용 가능 수·생성 수·판정 가능 수를 함께 보고한다. 각 조건의 전체 표와 공통으로 판정 가능한 paired 결과를 모두 보인다. 어려운 문장을 분모에서 빼거나 판정 불가 증가를 개선으로 포장하지 않는다.

계산 권한·개인정보·상태 무결성에 회귀가 있는 후보는 제외한다. 나머지는 기존 사전 고정된 후보 선택 규칙을 따른다. 축별 우열이 엇갈리면 임의 가중 평균으로 승자를 만들지 않는다. 필요하면 “미채택”을 정상 결과로 기록한다. [M2][M7]

문법 오탐을 수정해야 한다면 기존 응답·기존 점수는 보존한 새 버전으로 모든 해당 조건에 동일하게 적용한다. 결과를 본 후 유리한 응답에만 새 규칙을 적용하지 않는다.

## 9. S6: 새 질문과 실제 후보 앱 확인

기존 계획의 새 합성 24개는 질문 변형·부모 대화·출생 seed 계열 단위로 분리한다. P1·입력 정책·검사 기준·후보를 정한 뒤 한 번 사용한다. 사용한 24개에 맞춰 다시 조정해 같은 묶음으로 향상을 주장하지 않는다. 소비된 sealed blind도 재사용하지 않는다. [M7]

기준 비교는 기존 R16/P0/C_FULL과 선택 후보 하나의 24 × 2 = 48요청이다. 실제 앱 요청·저장·표시 경로도 확인한다. 모의 생성기를 쓴 CPU 검사와 실제 모델 생성은 구분한다.

S3에서 확인한 R16/P1과 S4에서 확인한 3B/P0를 근거로, **시험하지 않은 3B/P1 조합이 이미 개선됐다고 가정하지 않는다.** 그런 조합이나 새로운 projection을 선택하려면 새 통합 후보임을 밝히고 평가 범위·선택 근거를 먼저 정한다. S6가 새로운 조합의 첫 실제 확인이라면 그 한계도 기록한다.

S6는 작은 합성 확인이다. 일반 사용자의 전체 정확도나 장기 대화 품질을 인증하는 시험이 아니다. 이후 데이터·학습을 바꿨다면 이미 사용한 S6를 새 독립 평가처럼 재사용하지 않는다.

## 10. 순서·예산·중단 규칙

| 작업 | 실행 조건 | 요청 상한 또는 산출물 |
|---|---|---|
| S3 | R16·P0/P1·동결 입력과 검사기 준비 | 96요청 |
| S4 | 모델 등록·동일 정밀도 실행 가능성 확인 | 192요청 |
| S5 | S3·S4 결과와 데이터 분포 대조 | 유지/재설계/보류 및 학습 여부 결정 |
| S6 | 후보 하나·새 질문·앱 경로 준비 | 48요청 |
| 별도 보정·학습 | S5에서 필요성이 확인되고 별도 실행 결정 | 범위 확정 전 자동 시작하지 않음 |

S3·S4·S6 본 비교의 합은 최대 336요청이다. 기존 전체 계획에는 적격성 확인을 포함한 상한과 이미 실행한 S2가 따로 있다. 새 프리플라이트·재사용·사전 차단을 실제 실행 manifest에서 대조하고, 미실행을 성공 생성으로 세지 않는다. 이 문서로 기존 총 예산을 자동 확대하지 않는다. [M7]

실행 불가, 근거 부족, 개선 없음도 기록 가능한 결과다. 다만 필수 S4 미실행을 전체 진단 완료로 표시하지 않는다. 진단 단계마다 지시문·검사기·데이터를 계속 바꿔 같은 질문을 반복하는 흐름을 피한다.
