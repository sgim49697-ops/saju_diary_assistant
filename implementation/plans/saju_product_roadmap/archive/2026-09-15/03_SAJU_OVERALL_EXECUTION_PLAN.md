## 1. 이번에 만들 제품의 최소 형태

전문 유료 명리 상담 전체를 복제하거나 모든 미래 사건을 맞히는 시스템이 아니라, 출생정보를 한 번 연결하고 승인된 계산 사실을 참고하면서 한국어 설명·일상 대화를 이어가는 경량 Assistant를 목표로 한다. 기존 제품 문서도 계산 사실과 해석 의견을 구분하고, 일기 저장·개인화·대운은 장기 방향으로 남겨 두고 있다. [O1]

이번 최소 사용 흐름은 다음과 같다.

1. 사용자가 출생정보를 입력하고 원국을 확인한다.
2. 원국이나 지원 날짜를 물으면 필요한 승인 사실을 사용한다.
3. 일반 공감·문장 작성으로 화제를 바꿔도 원국 연결 자체는 잊지 않는다.
4. 다시 사주를 물으면 올바른 현재 상태에서 이어간다.
5. 정정·시간 미상·지원하지 않는 계산을 임의 확정 없이 처리한다.

새 계산 기능의 수보다 이 흐름이 끊기지 않는 것을 우선한다. 다만 아직 측정하지 않은 자연스러움과 장기 개인화 품질을 완료했다고 표시하지 않는다.

| 계층 | 담당할 일 | 넘기면 안 되는 책임 |
|---|---|---|
| 계산기 | 승인 정책의 원국·일진·관계 사실과 불확실성 | 상담 문장과 사건 예측 |
| 세션·상태 | 현재 입력·원국·날짜·revision·연결 상태 | 이전 사실을 최신 사실처럼 묵시 재사용 |
| 요청 판별 | 지금 질문이 일반 대화·사실 조회·사주 설명·날짜 요청인지 구분 | 날짜 단어만으로 운세 의도를 확정 |
| Context Builder | 해당 작업에 필요한 사실과 이력만 전달 | 미지원 계산이나 임의 새 사실 생성 |
| 결정적 조회·표시 | 이미 확정된 필드의 정확한 값 표시 | 이 결과를 LLM 정답률로 보고 |
| LLM | 설명·공감·재작성·사실 활용 | 출생정보에서 계산 사실을 추측 |
| 자동 검사 | 측정 가능한 사실·상태·형식·경로 오류 판정 | 유한 규칙 통과를 전체 품질 인증으로 해석 |
| 운영 앱 | 승인된 버전의 일관된 실행·저장·표시 | CPU 테스트 통과만으로 서비스 자동 교체 |

세 계층의 의사결정을 섞지 않는다. **계산 기능이 존재하는가**, **그 사실이 현재 대화에 연결됐는가**, **지금 질문에서 그 사실이 필요한가**는 각각 다른 질문이다.

## 4. 앱 우선 과제: 날짜가 포함된 일상 대화의 오차단

### 4.1 현재 문제가 생기는 구조

v1.16의 `prompt_intent()`는 일부 일반 대화 표현을 먼저 인정하고, 그에 걸리지 않는 날짜 표현을 기간 요청으로 처리할 수 있다. 날짜 검사는 모델 생성보다 먼저 수행된다. 따라서 큰 모델을 붙여도 호출 전에 차단되면 해결되지 않는다. [O4][O5]

아래는 이전 검토의 분리 로직 재현에서 남은 사례를 바탕으로 한 개발 회귀 목록이다. 실제 서비스 전체를 새로 실행해 검증한 결과가 아니며, 이번 문서에서는 후속 테스트의 기대 처리로 사용한다.

| 입력 | 후속 후보의 기대 처리 | 날짜 계산 검사가 필요한가 |
|---|---|---|
| 오늘 야근했어 | 일반 공감 대화 | 아니오 |
| 어제 영화 보고 왔어 | 일반 대화 | 아니오 |
| 내일 면접이라 긴장돼 | 공감·면접 준비 대화 | 아니오 |
| 이번 주에 운동 시작했어 | 일반 대화 | 아니오 |
| 내일 점심은 뭘 먹지? | 일반 대화 | 아니오 |
| 사주 말고 그냥 들어줘 | 사주 제외 일반 대화 | 아니오 |
| 내일 운세를 봐줘 | 명시적 날짜 사주 요청 | 예 |
| 사주 말고 내일 운세를 알려줘 | 별도로 남은 운세 요청 | 예 |
| 오늘은 힘들었어. 내일 운세는 어때? | 일상 설명과 내일 운세 요청 분리 | 활성 운세 요청의 내일에만 적용 |
| 그럼 내일은 어때? | 이전 주제가 명확하면 참조, 아니면 최소 확인 | 운세 의도가 확정된 경우에만 적용 |

“오늘 야근했어”가 연결 날짜와 같아서 통과하는 경우에도, 운세 의도로 잘못 분류했다면 정상 동작으로 평가하지 않는다.

### 4.2 구현할 원칙

1. 날짜는 시간 정보이지 그 자체로 운세 의도가 아니다.
2. 명시적으로 제외한 사주 주제와 별도로 남은 능동 운세 요청을 구분한다.
3. 날짜 추출·범위 검사는 활성 계산 요청에 적용한다. 다른 절의 일상 날짜까지 묶어 다중 날짜 요청으로 만들지 않는다.
4. 문맥이 없거나 애매하면 제한된 확인을 사용한다. 모든 모호한 문장을 운세로 단정하거나 일반 대화로 조용히 통과시키지 않는다.
5. `흐름`, `해석`, `오늘`, `내일` 같은 넓은 단어 하나를 충분한 운세 근거로 보지 않는다.
6. snapshot이 전달됐다면 의도와 무관하게 무결성 검증을 유지한다. 주제 제외 문구가 권한 우회로가 되면 안 된다.

이 작업의 목표는 모든 한국어 의도를 완벽히 이해하는 새 분류기를 만드는 것이 아니다. 확인된 오차단 유형을 닫고, 명시적 요청·일반 대화·애매한 후속의 처리 원칙을 나누는 것이다. 정규식의 일반 단어 목록을 끝없이 늘리는 방식에 의존하지 않는다.

## 5. 원국 연결 상태와 응답 모드를 분리한다

### 5.1 현재 연결 구조와 변경 제안

현재 후보는 원국이 연결된 대화에 bound 프로필을 사용하고 시스템 메시지에 runtime 컨텍스트를 함께 붙인다. 일반 대화로 분류해 차단을 피하는 것과, 일반 대화에 맞는 최종 모델 입력을 만드는 것은 다른 작업이다. [O5]

제안하는 분리는 다음과 같다.

```text
서버가 보관하는 상태
  출생정보 · 승인 원국 · 선택 날짜 · revision · 근거 · 연결 이력

현재 요청에 맞춘 응답 계획
  일반 대화 / 단순 사실 조회 / 원국 설명 / 날짜 설명 / 확인 필요

실제 모델 입력
  해당 작업의 지시 + 필요한 승인 사실 + 필요한 대화 이력
```

이는 개념 설계다. 기존 HMAC·binding·schema·권한 검증을 통과하지 않은 새 JSON을 그대로 모델에 전달하라는 의미가 아니다.

### 5.2 모드별 동작

| 응답 모드 | 제공 정보 | 응답 방식 |
|---|---|---|
| 일반 대화·공감·재작성 | 현재 요청과 필요한 일반 대화 이력 | 사주를 강요하지 않는 LLM 응답 |
| 단순 사실 조회 | 명시적으로 식별한 승인 필드 | 프로그램이 값을 정확하게 출력하거나 필요한 짧은 설명만 LLM에 위임 |
| 원국 설명 | 질문과 관련된 원국 사실·불확실성 | 승인 사실과 참고 해석을 구분 |
| 날짜 흐름 설명 | 선택 날짜의 승인 사실과 필요한 원국·관계 사실 | 실제 제공된 범위에서 설명 |
| 의도·날짜 확인 필요 | 확인에 필요한 현재 상태 | 부족한 항목만 확인 |
| 미지원 계산 포함 | 미지원 사유와 처리 가능한 요청 부분 | 계산 추측 없이 가능한 일반 요청 수행 |

단순 조회는 의미가 명확하고 필드가 유일하게 정해진 경우부터 도입한다. 모델이 “나는 맞게 필드를 골랐다”고 말한 사실만으로 결정적 조회를 승인하지 않는다. 새로운 다단계 에이전트나 별도 대형 라우터를 기본 의존성으로 추가하지 않는다.

### 5.3 원국이 없어지는 것이 아니라 불필요한 전달을 줄이는 것이다

일반 대화에서 사주 사실을 생략해도 서버의 원국 연결 상태는 유지한다. 사용자가 다시 사주를 요청하면 현재 revision의 사실을 가져온다. 일반 대화 전환을 이유로 원국을 삭제하거나 다시 출생정보를 물어보지 않는다.

반대로 “아까 말한 을목을 더 쉽게 설명해줘”처럼 이전 사주 설명을 지칭하는 질문에는 관련 사실과 필요한 이력을 유지한다. 현재 문장에 `사주`가 없다는 이유만으로 모든 사실을 제거하지 않는다.

### 5.4 응답 계약을 바꿀 때의 원칙

제품 후보에서는 “단순 일진 조회에도 원국 사실 하나를 반드시 붙인다” 같은 불필요한 의무를 요청 유형에 맞게 완화할 수 있다. 그러나 이 변경은 기존 S3·S4의 사실 지표를 사후 수정하는 수단으로 사용하지 않는다.

새 제품 계약을 먼저 정의하고 같은 기준으로 후보와 기준선을 비교한다. 과거 답변·점수는 보존한다. 단순 사실 표시의 정확도, 모델 자체 사실 활용, end-to-end 요청 성공을 별도 지표로 둔다.

## 6. 정정·날짜 변경·대화 이력

### 6.1 현재 제한을 유지하면서 개선한다

현재 연결 대화는 원국·날짜 snapshot이 달라지면 재사용을 제한하고 새 연결을 요구한다. 이는 이전 사실과 현재 사실이 섞이는 것을 막기 위한 보호다. [O5]

이번 후보에서는 기존 snapshot을 덮어쓰지 않는다. 정정·날짜 변경이 생기면 새로운 검증된 binding을 만들고, 사용자에게 현재 연결 대상이 바뀌었다는 사실을 명시한다. 기존 구현이 새 대화를 요구한다면 우선 그 계약 안에서 UI 흐름을 개선한다.

### 6.2 이력을 옮길 때 보존할 것과 제외할 것

| 이력 종류 | 처리 방향 |
|---|---|
| 사용자의 일반 이야기·요청 | 필요한 범위에서 유지 가능 |
| 이전 원국에 근거한 모델 설명 | 현재 사실로 재주입하지 않음 |
| 사용자가 정정한 정보 | 새 revision의 근거로 반영하되 원문 공개 금지 |
| 이전 모델 오답 | 현재 정답과 구분되는 과거 발언으로만 취급 |
| 날짜가 달라진 일진 설명 | 새 날짜 설명의 현재 근거로 사용하지 않음 |

자동 요약을 추가하면 요약 자체의 사실 오염을 검사해야 한다. 이번 첫 후보에서는 대규모 장기 메모리·자동 일기 저장을 새 의존성으로 추가하지 않는다.

### 6.3 날짜 정책을 별도 문제로 다룬다

v1.5 단일 일진의 실제 요청 하한은 release 하한과 서버 KST 오늘 중 늦은 날짜다. 검증 자료가 있다고 과거 날짜 조회가 현재 허용되는 것은 아니다. [O6]

따라서 과거 일진 요청은 현재 정책대로 제한하되, 과거의 일상 이야기는 정상적으로 처리한다. 과거 일기 날짜에 일진을 붙이는 기능은 별도의 정책·연결 범위 변경으로 판단한다. 이를 위해 계산 정밀도 전체를 다시 개발하지 않는다.

## 7. 두 작업을 섞지 않고 진행하는 실행 순서

앱 개선과 모델 진단은 병행할 수 있지만 같은 결과표에 섞지 않는다. 아래 작업 구분은 추가 Phase를 만드는 것이 아니라 기존 계획의 책임과 의존성을 설명한다.

| 순서 | 작업 | 주요 산출물 | 의존 관계 |
|---|---|---|---|
| 1 | 기준선 확인·계산기 동결 | 현재 코드/기록/후보 구분과 계산기 재개 조건 | 현재 정본·release 확인 |
| 2A | 앱 날짜 오차단 수정 | 기존 회귀와 새 일반 대화 사례의 CPU 결과 | 모델·계산값·S3 입력은 변경하지 않음 |
| 2B | S3 지시문 비교 | P0/P1 항목별 개선·회귀 | 동결 R16·C_FULL·부모 이력 |
| 3 | S4 규모×정보 비교 | K0와 3B의 2×2 결과·자원 비용 | S3 뒤 진행, 공통 P0·실행 가능성 확인 |
| 4 | 입력·응답 모드 후보 정리 | 최소 앱 후보 하나와 변경 목록 | 앱 회귀와 S3·S4 결과 참조 |
| 5 | S5 데이터·학습 판단 | 400건 유지/재설계/보류, 재학습 여부 | 남은 오류 위치와 학습 커버리지 대조 |
| 6 | S6 새 질문·실제 후보 경로 확인 | 24문항 × 2경로와 통합 한계 | 후보·평가 계약 동결 |
| 7 | 제한 운영 반영 여부 결정 | 채택 또는 미채택·되돌림 경로 | 실제 모델/앱 확인과 별도 실행 결정 |

중요한 순서 제약은 **S3를 반복하느라 S4를 미루지 않는 것**이다. 앱 모드 분리의 전체 구현이 끝날 때까지 S4를 기다릴 필요도 없다. 진단은 기존 입력 경로에서 수행하고 제품 후보는 별도로 확인한다. [O7][O8]

새 보정·학습은 자동 후속이 아니다. S5에서 별도 학습을 결정했더라도 현재 진단의 S6와 새 학습 검증을 같은 완료 기록으로 합치지 않는다. 이미 사용한 새 질문을 다음 모델의 독립 확인으로 재사용하지 않는다.

## 8. 평가를 세 층으로 구분한다

### 8.1 계산·상태 정확성

고정 입력의 계산값·불확실성·revision·무결성을 검사한다. 승인 범위의 기술적 계약 검증이며 운세 해석의 정답률이 아니다.

### 8.2 모델 단독 진단

동일한 질문·사실·부모 이력에서 모델이 생성한 원응답을 평가한다. 앱이 직접 채운 사실이나 재시도 후 교정 답변을 원모델의 성공으로 세지 않는다. S3·S4에서 이 층을 고정한다.

### 8.3 실제 앱 요청 수행

사용자 요청이 올바르게 처리돼 최종 화면까지 도달했는지 평가한다.

| 지표 | 의미 | 피해야 할 착시 |
|---|---|---|
| 일반 대화 오차단 | 운세 계산이 아닌 요청을 잘못 막았는가 | 생성하지 않았으니 안전하다고 성공 처리 |
| 불필요한 확인 | 명확한 요청에도 계속 되묻는가 | 모든 요청을 애매함으로 보내 오차단을 줄임 |
| 미지원 요청 보호 | 계산 범위를 벗어난 요청에서 허위 사실을 만들지 않는가 | 일반 대화 허용을 이용해 계산 제한 우회 |
| 요청 수행 | 공감·메시지 작성·짧은 답·주제 전환 | 사실을 하나 말했으니 요청도 성공이라고 판단 |
| 사실 활용 | 역할과 값·최신 상태가 맞는가 | 정답 문자열이 포함됐다는 이유만으로 통과 |
| 원응답/표시 일치 | 저장·API·화면에서 내용이 달라지는가 | CPU 모의 경로 통과를 live 전체 검증으로 간주 |
| 지연·메모리 | 동일 조건에서 실제 비용이 어떤가 | 모델 로딩 시간과 warm 생성 시간을 혼합 |

모든 지표는 적용 가능한 분모와 `PASS / FAIL / UNSCORABLE` 또는 해당 상태를 함께 보고한다. 미측정 자연스러움은 `not_measured`로 둔다. 임의 종합점수나 새 인간 평가 의무를 추가하지 않는다.

## 9. 구현·통합 확인 체크리스트

### 9.1 앱 CPU 회귀

- 날짜 포함 일상 대화와 명시적 날짜 운세 요청을 구분한다.
- 주제 제외 후 별도 운세 요청, 섞인 날짜, 문맥이 필요한 후속을 확인한다.
- 정상 일반 대화를 불필요하게 날짜 선택 화면으로 보내지 않는다.
- 변조 binding·stale revision·미지원 범위는 계속 보호한다.
- 일반 대화에서는 무관한 원국 설명을 강제하지 않는 입력이 만들어진다.
- 일반 대화 뒤 사주로 돌아오면 최신 원국·날짜를 사용한다.
- 생시 미상·부분 결과를 exact day binding에 몰래 넣지 않는다.
- 기존 부모 코드·보고서·세션을 변경하지 않는지 확인한다.

기존 25개 후보 회귀를 없애지 않고, 새로 확인된 실패 유형과 최소 표현 변형을 보완한다. 새로운 거대한 검사 프레임워크를 만드는 것을 선행 조건으로 삼지 않는다. [O3]

### 9.2 실제 모델·앱 통합

실제 후보 worker·모델 loader·tokenizer·adapter·최종 입력·원응답·저장·화면을 같은 요청에서 확인한다. 모델을 부르지 않는 사실 조회·확인 응답과 모델 생성 응답을 분리해 기록한다.

앱 전체의 요청 수를 보고할 때는 모델 생성, 프로그램 직접 응답, 확인 요청, 예상 차단, 예상 밖 차단/실행 오류, 미실행을 구분한다. 직접 응답 때문에 GPU 요청이 줄어든 것은 제품 비용 개선일 수 있지만 모델 추론 능력 향상은 아니다.

S3 96, S4 192, S6 48의 기존 본 비교 상한을 유지한다. 별도 앱 CPU 회귀는 새 GPU 생성이 아니다. 통합 확인에 추가 GPU 요청이 필요하면 해당 범위와 비용을 사전에 따로 등록하고 기존 48요청 안에 숨기지 않는다. [O8]

### 9.3 종료·채택 판단

| 판단 | 조건과 처리 |
|---|---|
| 진단 완료 | 실행한 비교·제한·다음 선택이 기록됨. 개선 없음도 결과 |
| 앱 후보 확인 완료 | 사전 정의한 경로와 안전·상태 회귀를 확인. 모의/실제 실행 범위 구분 |
| 후보 미채택 | 사실·상태·개인정보 회귀 또는 지표 충돌·판정 근거 부족을 기록 |
| 운영 반영 검토 | 실제 후보가 확인됐고 사용 범위·모델·입력·되돌림 경로가 명확함 |
| 운영 반영 완료 | 별도 승인된 서비스 전환과 실행 신원 확인까지 실제 수행됨 |

실험 실패를 이유로 검사 기준을 계속 완화하지 않는다. 반대로 미래의 모든 품질을 증명할 때까지 현재 진단이 끝나지 않는 구조도 만들지 않는다. 작은 합성 평가의 통과를 전체 사용자의 품질 보장으로 확대하지 않는다.

- private 출생정보·응답·키·checkpoint를 공개 문서나 원격 저장소에 넣지 않는다.

## 12. 이번 회차 이후 남겨야 할 결론

최종적으로 다음 다섯 질문에 답할 수 있어야 한다.

1. 계산기를 다시 손댈 실제 이유가 있는가, 아니면 현재 범위로 충분한가?
2. 어떤 정상 요청이 앱에서 잘못 처리됐고 후보에서 어떻게 달라졌는가?

4. 남은 오류는 입력·데이터·규모 중 어디를 바꾸는 것이 타당한가?
5. 유지할 후보 하나 또는 미채택 사유와 다음 최소 작업은 무엇인가?
