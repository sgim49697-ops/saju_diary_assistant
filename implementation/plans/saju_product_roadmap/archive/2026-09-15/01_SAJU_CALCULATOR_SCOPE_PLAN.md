이번 작업은 계획문서 작성이다. 아래 구현·시험·승인 절차는 후속 작업이며, 이번 작성으로 새 계산·모델 실행·배포를 수행하거나 승인한 것은 아니다. 운영 상태와 기존 검증 수치는 저장소 기록을 기준으로 한다.

## 1. 계산기의 역할과 이번 목표

계산기는 사용자가 선택한 출생정보와 계산 정책에 따라 원국·일진·관계 사실을 반환하는 구성요소다. 전통적 해석이나 실제 미래 사건의 발생을 보장하는 구성요소가 아니다.

이번 목표는 계산기를 더 넓고 정밀하게 만드는 것이 아니라 다음 경계를 명확히 하는 것이다.

1. 지금 사용할 수 있는 사실은 무엇인가.
2. 확정할 수 없는 경우 어디까지 반환하고 어디서 멈추는가.
3. 어떤 문제가 발생했을 때만 계산기 개발을 다시 여는가.

계산 결과가 정확한데 모델이 다른 일간을 말하거나, 일상 대화가 날짜 조건 때문에 차단되는 경우는 계산 정밀도 개선 대상이 아니다. 계산값·상태·전달·응답 중 오류가 처음 생긴 위치를 먼저 확인한다. [C1][C7]

## 2. 현재 확인된 기준선

### 2.1 계산 정책과 승인 범위

| 영역 | 현재 확인된 범위 | 오해하면 안 되는 점 |
|---|---|---|
| 지역·시간 정책 | `country_code=KR`, `Asia/Seoul`, `KR_CIVIL_MIDNIGHT_V1` | 해외 출생·다른 계산 관례까지 승인한 것이 아님 |
| 원국 | 정규화 양력 `1920-01-07~2026-08-31`의 제한 승인 | 최신 날짜까지 자동으로 확장되는 범위가 아님 |
| 입력 불확실성 | 정확한 시각·시간 범위·생시 미상 구분 | 시간 미상을 임의의 시각으로 대체하지 않음 |
| 경계 정책 | 연은 입춘, 월은 12절, 일은 민간시 00:00, 시주는 민간시 | 진태양시·균시차를 적용하는 다른 관례와 동일하다고 주장하지 않음 |
| 단일 일진 자료 | `2026-09-02~2049-12-31`, KST 정오의 연·월·일 간지 | 하루의 모든 시각에 적용되는 정밀 절입 결과가 아님 |
| 기간 계산 | 1~31일의 일별 배열 구현·검증 기록 | 월 전체 길흉이나 기간 종합 해석까지 승인한 것이 아님 |
| 단일 날짜 관계 | 정해진 규칙에 따른 십신·합·충·형·파·해 등의 직접 관계 존재 | 관계가 있다는 사실과 사건·길흉 판단은 다름 |
| 미승인 기능 | strict/full, 미래 물리 절입 시각, 대운 등 제한 유지 | 기능 플래그를 켜는 것만으로 승인 범위를 넓힐 수 없음 |

위 정책의 과거 이력은 Runtime 정본, 최신 완료 범위는 `00-current-baseline.md`와 각 release가 소유한다. Runtime 정본의 과거 상단 설명만 읽고 이후 기간·관계 구현이 미완료라고 판단하지 않는다. [C1][C2][C3][C4]

### 2.2 검증 자료 범위와 실제 요청 허용 범위를 구분한다

단일 일진 v1.5에는 아래 정책이 실제 구현돼 있다.

```text
실제 단일 일진 요청 하한 = max(2026-09-02, 서버의 KST 오늘)
```

따라서 서버 날짜가 2026-09-15라면, 검증 자료에 2026-09-02가 포함돼 있어도 현재 정책으로 그날을 새로 계산하는 요청이 허용된다는 뜻은 아니다. 승인 자료의 범위, 계산 도구의 요청 허용 범위, 대화에 이미 연결된 snapshot의 날짜를 따로 표시한다. [C5]

과거 일기를 위한 일진 조회가 필요해지면 이는 우선 **과거 날짜 사용 정책과 앱 연결 방식의 변경**이다. 절입 정밀도를 더 높여야만 해결되는 문제로 취급하지 않는다. 기존 과거 날짜 차단을 임의로 해제하지 않고 필요한 기능 범위를 별도로 정한다.

### 2.3 기존 검증 결과를 사용하는 방식

원국 보고서는 exact 계산 77,908건 실패 0, 경계 probe 2,558건 실패 0을 기록한다. 동시에 과거 원시 분 라벨 불일치 14건을 숨기지 않고, 경계 분 50개를 격리한다. “50분”은 모든 절입 전후 50분을 일괄 차단한다는 의미가 아니다. [C6]

일진 release에는 8,522일 label 불일치 0, 최신 기준선에는 기간 263,717개 연속 구간의 검증 완료가 기록돼 있다. 이 수치는 해당 검증 계약의 결과이며 실제 이용자 전체에 대한 오답률이나 해석의 정확도가 아니다. 이번 문서 작성에서 전수 계산을 다시 수행하지 않았다. [C1][C4]

## 3. 동결할 것과 계속 고칠 것

### 3.1 즉시 동결할 범위

- 이미 승인된 v1.4·v1.5 및 기간·관계 release의 계산값·부모 관계·원본 보고서.
- 현재 계산 관례와 지역 범위. 진태양시나 다른 일 경계를 새 기본값으로 추가하지 않는다.
- 드문 경계 사례의 잔여 불확실성을 없애기 위한 정밀도 경쟁.
- 현재 사용자 흐름에 필요성이 확인되지 않은 연도·대운·관계 해석 확대.
- 모델이 사실을 잘못 쓰는 문제를 해결하기 위한 계산기 재작성·외부 라이브러리 교체.

“동결”은 소스 변경을 영구 금지한다는 의미가 아니라, 새 기능과 추가 정밀화를 기본 개발 과제에서 제외한다는 의미다.

### 3.2 계속 고쳐야 하는 문제

| 문제 | 처리 원칙 |
|---|---|
| 승인 범위의 동일 입력에서 잘못된 기둥·일간·일진 반환 | 최소 재현 사례와 독립 기대값으로 원인 확인 후 수정 |
| 양력·음력·윤달·시간대 정규화 오류 | 입력 정규화 계층부터 수정. 모델이 보정하게 하지 않음 |
| 생시 미상을 임의의 시주로 확정 | 불확실성 전달을 복구. 값을 추측해서 채우지 않음 |
| 생일 정정 이후 이전 계산값이 재사용됨 | 상태·캐시·binding 문제인지 계산 문제인지 분리 |
| 만료·변조된 근거 또는 잘못된 권한의 승인 처리 | 기존 검증·권한 경계를 유지하며 수정 |
| 입력 오류나 미지원 조건 때문에 프로세스가 비정상 종료 | 명시적 오류·제한 상태로 반환하도록 수정 |

계산값이 바뀌는 수정은 기존 승인 파일을 덮어쓰지 않는다. 영향 범위를 검증한 별도 후보와 필요한 새 release로 처리한다. 기존 report·checkpoint·완료 이력은 보존한다.

## 4. 타협 가능한 것과 불가능한 것

| 구분 | 타협 가능한 선택 | 허용하지 않는 처리 |
|---|---|---|
| 지원 범위 | 한국·고정 날짜 범위·단일 정책으로 제한 | 범위 밖 결과를 범위 안의 승인 사실처럼 반환 |
| 정밀도 | 정오 기준 날짜 label, 분 단위 입력, 명시적 불확실성 | 불확실한 경계에서 임의로 한쪽을 정답으로 확정 |
| 생시 미상 | 승인된 안정 사실만 설명하거나 일반 대화로 전환 | 생시를 12:00 등으로 채워 완전한 원국인 척함 |
| 해석 | 계산 사실과 참고 해석을 구분 | 관계 존재로 재물·건강·직업 사건을 확정 |
| 운영 범위 | 미지원 계산을 제한하고 가능한 일반 요청은 수행 | 계산 불가를 이유로 관계없는 일상 대화까지 중단 |
| 검증 비용 | 변경 범위에 맞는 회귀와 기존 근거 재사용 | 검증하지 않은 범위를 검증 완료라고 표시 |

핵심은 **정답을 느슨하게 만드는 것이 아니라 제품이 책임지는 범위를 줄이는 것**이다.

## 5. 불확실성과 부분 결과 처리

### 5.1 기본 처리 원칙

계산 결과는 현재 존재하는 `status`, `hard_facts`, `stable_facts`, `uncertainty`, `limitations`, `fact_authority` 등의 의미를 보존한다. 아래는 동작 설계이지 새 필드를 기존 승인 schema에 바로 넣으라는 지시가 아니다. [C2][C7]

| 상황 | 계산 계층 | 앱·모델 계층에 요구할 동작 |
|---|---|---|
| 정상 승인 입력 | 현재 승인 사실 반환 | 해당 사실의 역할과 값을 그대로 사용 |
| 시간 범위 안에서 일부만 안정 | 승인 정책이 허용하는 공통 사실과 불확실성 반환 | 확정 가능한 항목만 설명 |
| 절입 경계가 불안정 | 현재 차단·불확실성 처리 유지 | 임의 원국 생성 금지. 계산과 무관한 대화는 별도로 가능 |
| 시주를 알 수 없음 | 시주를 확정하지 않음 | 시주가 필요한 결론을 피하고 제한을 짧게 안내 |
| 미승인 날짜·지역·기능 | 미지원 사유 반환 | 제공 가능한 요청 부분과 미지원 부분을 분리 |
| 변조된 snapshot·권한 | 무결성 검증 실패 | 일반 대화 모드를 이유로 검증을 우회하지 않음 |

### 5.2 부분 결과와 기존 day binding의 호환성을 가정하지 않는다

현재 v1.5의 단일 일진은 승인된 exact 원국과 결합하는 계약이다. 원국에서 부분 결과가 가능하다는 이유만으로 동일한 day binding에 그대로 넣으면 안 된다. [C2]

이번 기본 범위에서는 기존 계약을 보존한다. 부분 원국의 날짜 해석이 제품에 꼭 필요해질 때만 별도 연결 계약과 평가 범위를 정의한다. 그 전에는 승인된 원국 부분 설명이나 일반 대화를 제공하는 방향으로 제한한다.

## 6. 검증 비용을 줄이는 운영 원칙

### 6.1 변경 유형별 검증 수준

| 변경 유형 | 필요한 확인 | 반복하지 않아도 되는 작업 |
|---|---|---|
| 문서·지시문만 변경 | 링크·기준선·출력 계약 확인, 계산 관련 변경 없음 확인 | 불변 천문 자료 재수집·동일 전수 계산 |
| 의도 판별·일반 대화 라우팅 변경 | 정상/미지원 요청·binding 무결성 회귀, 계산값 불변 확인 | 원국 엔진 전체 재작성 |
| snapshot projection 변경 | 필드 의미·역할·불확실성 보존, 금지 필드 비노출 | 실제 계산 공식 변경 |
| 계산·시간 정책·공식 자료 변경 | 영향 범위 독립 기대값·경계 회귀·해당 release 검증 | 관련 없는 모델 재학습의 자동 실행 |
| 계산 의존성·운영 환경 변경 | 로딩·결정성·고정 결과·필요한 호환성 검사 | 근거 없는 “같은 버전이니 동일” 가정 |

기존 파일의 hash 일치는 원본과 같다는 근거이지, 계산 내용의 정당성을 새롭게 증명하는 검증은 아니다. 변경하지 않은 산출물의 기존 검증 근거를 재사용하고, 실제 변경이 있을 때 필요한 검증을 다시 한다.

### 6.2 회귀 집합의 구성

기존 테스트를 우선 재사용한다. 새로운 대규모 Gate를 만들기보다 다음 유형의 빠진 사례만 보완한다.

- 승인 범위의 일반 입력, 양력·음력 정규화, 윤달 확인 필요 입력.
- 일 경계·절입 경계·시간 범위·생시 미상.
- 서버 KST 기준일 전후와 승인 날짜 상한·하한.
- 동일 입력 반복, 정정 후 최신 revision, 오래된 binding, 세션 간 혼합.
- 무결성 실패, feature off, 미지원 범위.

테스트 기대값은 시험 대상 함수의 출력을 그대로 복사해 만들지 않는다. 고정된 독립 근거 또는 이미 검증된 정책 결과를 사용한다. 경계 50개나 기존 불일치를 숨기는 방향으로 기대값을 변경하지 않는다.

|---|---|---|
| 승인 범위 실제 오답 재현 | 계산값 자체가 잘못됐는가, 전달·표시 오류인가? | 최소 재현·독립 기대값·영향 범위 |
| 현재 제한이 목표 사용자를 실제로 막음 | 더 정밀한 계산이 필요한가, 지원 정책·앱 연결만 필요한가? | 대표 요청과 최소 지원 범위 |
| 공식 자료·의존성 변경으로 기존 전제가 깨짐 | 어떤 승인 결과에 영향을 주는가? | 영향 분석과 회귀 결과 |
| 다음 제품 범위를 명시적으로 확정 | 기존 기간·관계 구현 재사용으로 충분한가? | 기능 범위·비용·별도 실행 결정 |

예를 들어 2026-08-31 이후 출생 입력 지원이나 과거 일진 조회가 필요해지면 해당 범위만 검토한다. 이를 계기로 해외 시간대·대운·모든 계산 관례를 한꺼번에 개발하지 않는다.

투자 우선순위는 “영향받는 실제 요청 규모 × 오류 심각도 × 사용자 경험 개선”을 기준으로 판단한다. 실제 사용 분포가 없으면 수치나 오답률을 만들어내지 않고 제한된 진단 근거임을 밝힌다.

## 8. 후속 작업과 종료 조건

아래 C-표기는 이 문서 내부의 작업 목록이며 기존 Phase나 S단계를 대체하지 않는다.

| 작업 | 산출물 | 종료 조건 |
|---|---|---|
| C-A. 범위 동결 정리 | 현재 승인 범위·시간 정책·미지원 기능 표 | 원국/일진 자료 범위와 실제 요청 범위가 분리됨 |
| C-B. 오류 경계 정리 | 계산·상태·라우팅·모델 오류 분류 | 최근 대화 오류를 계산기 과제로 잘못 넘기지 않음 |
| C-C. 유지보수 기준 지정 | 변경 유형별 회귀·재개 조건 | 동일 전수 검증을 반복하지 않아도 될 조건이 명확함 |
| C-D. 앱 전달 조건 확인 | 안정 사실·불확실성·revision 전달 요건 | 현재 schema를 위반하는 묵시적 범위 확대가 없음 |

기존 회귀가 유효하고 새 계산 결함이 없으면 계산기 작업은 여기서 종료한다. “모든 연도·모든 경계·모든 해석이 완벽해질 때”를 종료 조건으로 삼지 않는다.
