# Phase 9 / S4 실행기 구현 기록

## 범위와 실제 상태

사용자의 현재 구현 확인·후속 구현 요청에 따라 원본 `master`의 `7a7cd9ab7535ddd4fb930077e6362dafc8fe9dbe`에서 시작했다. [Phase 9](../plans/saju_product_roadmap/phases/phase-09.md)의 실행기·공식 모델 등록·CPU 회귀를 구현했다. 새 분기·worktree를 만들지 않았으며 원본 ZIP·기존 작업 세션·서비스를 보존한다.

**실제 비교 미실행, GPU 생성 0**이다. 3B의 공식 공개 metadata·라이선스·파일 hash는 확인했지만 가중치는 다운로드하지 않았다. 모델 다운로드와 최대 192요청 GPU 비교의 구체적 범위는 사용자에게 확인 요청했으며 회신 전까지 실행하지 않는다. CPU 모의 검증 통과를 실제 모델 로딩·dry-run·성능 검증으로 표시하지 않는다. 원문 반영표의 Phase 9 실제 비교 과제 `M-0293`·`O-0173`은 `not_executed`를 유지한다.

기존 438요청을 소비한 상태에서 계획상 잔여는 **242 = S4 192 + S6 48 + 공유 적격성 2**로 그대로다. 이번 CPU 테스트는 요청 예산을 소비하지 않는다. 학습·데이터 보정·운영 교체·계산 release 변경·새 24문항·소비된 sealed blind 접근은 없다.

## 등록과 비교 조건

공식 [모델 카드](https://huggingface.co/kakaocorp/kanana-2-3b-instruct), 고정 revision의 [config](https://huggingface.co/kakaocorp/kanana-2-3b-instruct/blob/6a5d7889964c4c590299d16e309eabab1f73f8a9/config.json)·[라이선스](https://huggingface.co/kakaocorp/kanana-2-3b-instruct/blob/6a5d7889964c4c590299d16e309eabab1f73f8a9/LICENSE)와 공식 Hub 파일 metadata를 확인해 [진단 전용 등록](../../configs/model_versions/saju_1b_baseline/kanana-2-3b-s4-v1.0.0.json)을 추가했다. 앱 모델 registry는 바꾸지 않는다.

- 모델 ID `kakaocorp/kanana-2-3b-instruct`, revision `6a5d7889964c4c590299d16e309eabab1f73f8a9`; 실제 파라미터 3,508,972,032개, BF16 가중치 2개 shard다. config·index·tokenizer/template·LICENSE·README·generation config까지 10파일의 총 등록 크기는 **7,028,155,860바이트**다. 각 파일의 크기·SHA-256을 등록했고 다운로드 후 같은 pin을 다시 검증한다.
- 등록 JSON SHA-256은 `f20ef62aa8f83b288f669d12d20622bcb6a6eed11db356960db778c81c73a9c9`다. 원격 mutable `main`으로 수집하지 않으며 기존 파일이 다르면 자동 덮어쓰지 않는다. 중간 cache·최종 경로의 symlink, 경로 이탈, 부족한 공간·중복 수집을 거부한다.
- 공식 명칭은 **Kanana Open License Agreement**다. 고정 원문과 사용 제한을 확인한 뒤 합성 로컬 진단 후보로 등록한 프로젝트 판단이며, 법률 자문·모델 재배포·모든 서비스 사용의 권리 판단은 아니다. 실제 배포는 별도 검토 범위다.
- 3B는 `Qwen3ForCausalLM`·32개 full attention·native 32,768이며 custom code를 실행하지 않는다. K0는 기존 고정 `Kanana2TinyForCausalLM`·24개 sliding/8개 full attention·검증된 로컬 custom code를 유지한다. 따라서 순수 파라미터 수만의 효과가 아닌 규모·구성·학습 차이가 함께 있는 비교다.
- 설치된 `.venv`의 Transformers 4.57.6에서 native `Qwen3ForCausalLM` import를 확인했다. 실제 모델을 로딩한 검증은 아니다. 패키지·PyTorch·CUDA·기존 K0 환경을 변경하지 않았다.
- 양쪽 tokenizer/template를 각 공식 snapshot에서 독립 로딩한다. 고정 원격 파일 hash는 같지만 그 사실로 상대 tokenizer를 대체하지 않는다. CPU 회귀에서는 token ID가 다른 두 tokenizer도 동일 메시지를 유지하면 허용되는지 검증했다. 실제 3B 최종 입력과 길이는 아직 미검증이다.

## 구현한 실행 경로

1. [계약](../../configs/model_versions/saju_1b_baseline/system-context-s4-v1.0.0.json)과 `system_context_s4_contracts`가 S2/S3 불변 hash·48개·P0·FULL/MIN·권한을 고정한다. 기존 S3 파일과 결과는 고치지 않는다.
2. `system_context_s4_models`는 명시적 수집, 각 모델·코드·가중치·공식 tokenizer 검증을 담당한다. 다운로드는 기본 계획 출력이며 전용 환경값과 `--execute`가 함께 있어야 쓴다.
3. `system_context_s4_projection`은 동결 질문·facts·부모 이력·P0·projection을 유지하고 각 tokenizer로 다시 렌더링한다. K0는 S2의 원래 token과도 일치해야 하며 두 모델 사이 token ID 동일성은 요구하지 않는다. 입력 4,096·출력 4,096 상한, 이력 삭제 0을 유지한다.
4. [실행기](../../scripts/evaluation/system_context_s4.py)·backend는 **192요청 = 최대 172생성 + 기존 사전 차단 20**을 순차 처리한다. 각 모델 최장 적격 입력을 본 비교의 첫 두 요청으로 배치하며 추가 preflight는 0, 공유 잔여 2는 쓰지 않는다. 최초 둘 중 하나가 실패해도 비교를 강행하지 않는다.
5. 두 모델은 fresh `GenerationConfig()`와 동일한 명시적 greedy 인자를 사용해 모델 디렉터리의 숨은 decoding default를 제거한다. 이는 S4의 새 실행 신원에 기록되며 기존 S2 K0 출력을 재사용하지 않는다. P0·facts·S2 부모 이력·공통 생성 인자는 유지한다.
6. 전역 GPU lock·유휴·12GiB 여유·native JIT/header·BF16·CUDA device·cache 격리·300초 제한을 검사한다. 양자화·adapter·offload·임의 대체·재시도는 금지한다. 모든 worker는 오프라인으로 실행하며 다운로드와 생성 권한은 별개다.
7. 활성 build 원장이 192요청 예산을 고정한다. 검증된 완료만 재사용하고, 시작 marker만 남거나 오류가 기록된 요청은 재생성하지 않고 중단한다. 새 build로 예산을 초기화하지 않는다. private 0600/0700·동결 입력·응답 hash·공개 집계 전량 재계산·공개 allowlist를 검증한다.
8. 공개 집계는 모델×정보×층별 PASS/FAIL/UNSCORABLE, 양방향 대응쌍의 9종 판정 전이, 네 조건 모두 판정 가능한 사례의 모델 차이와 정보 조건별 차이를 제공한다. 제외된 판정 불가 분모도 기록하며 임의 가중 승자 점수는 만들지 않는다.

저장/API는 기존 K0 슬롯을 사용한 **CPU 문자열 소비 재생**으로만 표시한다. 이는 3B 앱 연결·브라우저 canary가 아니다. 시간은 모델 로딩을 포함하는 요청별 cold 측정이며 사전 파일 재해시 등의 전체 준비 시간이나 persistent warm 서비스 비용은 포함하지 않는다. warm은 미측정이고 이를 위해 추가 GPU 요청을 자동 배정하지 않는다.

## 검사기 보완과 한계

[scorer v1.2](../../scripts/evaluation/system_context_scoring_v1_2.py)는 기존 v1.1을 보존한 새 버전이다. S3에서 확인한 개념 설명의 전체 부정, 잘못된 사실을 새로 주장하지 않겠다는 부정 표현, 일반 요청에 끼어든 포괄적 원국 언급을 회귀로 보강했다. 독립 합성 표현·실제 긍정 오류·명시적 비사용·부정 범위 종료를 함께 검사하며 S3 원응답을 fixture에 복사하거나 S3를 재채점하지 않았다.

**22개 scorer 테스트**가 통과해도 유한 문법 검사다. 적용 범위 밖은 UNSCORABLE/`not_measured`로 유지하고 전체 정확도·자연스러움·해석 의미 품질을 주장하지 않는다. 해당 미측정을 새 완료 조건이나 사용자 작업으로 바꾸지 않는다. 새 응답을 본 뒤 같은 S4 build의 검사 규칙을 조정하지 않는다.

계약·192요청 plan·수집 계획 출력과 새 CPU **47개(검사기 22 + S4 25)**가 통과했다. 모의 192요청 완료·172번 모의 생성·완료 재개 192건 재사용, 실제 공개 파일 재계산과 변조 거부까지 확인했다. CPU 전용 환경에 `requests`가 없어 모의 다운로드 테스트 1개가 처음 실패했다. 테스트의 외부 다운로드 경계를 명시적으로 대체해 의존성을 분리한 뒤 47개 전부 통과했으며, 모델 파일 무결성·수집 인자 검사를 제거하지 않았다.

실제 `HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 .venv/bin/python -B -m scripts.evaluation.system_context_s4 execute` dry-run은 **exit 1 / blocked**였다. 원인은 로컬 3B snapshot의 `LICENSE`를 포함한 등록 파일이 아직 없기 때문이다. 자동 다운로드나 GPU 실행 없이 중단했으며 실제 모델 입력 재구성 통과로 기록하지 않는다.

문서 검사에서는 이전 “S4~S6 모두 미실행” 단일 표기 기대가 구현/실행 분리 표기와 충돌해 1개 실패했다. S4 실행기 구현·실제 비교 미실행·추가 수집 범위 확인과 S5~S6 미실행을 각각 요구하도록 갱신했다. 원문 hash·행별 대응·후속 미승인 상태 검사는 유지했다.

최종 관련 문서 **43개/0.350초**, 전체 ML 환경 unittest **1,044개/97.324초, 실패·오류·건너뜀 0**, Ruff·diff 검사를 통과했다. 이후 S3와 8A의 별도 `verify`도 위와 같은 공개 hash로 다시 통과했다. `git fetch origin master` 후 부모 `7a7cd9a`와 원격 차이 0을 확인했다. 실제 3B 모델 디렉터리·S4 raw/public build는 생성되지 않았다.

## 다음 실제 실행 순서 — 범위 확인 후에만

1. 이 구현·테스트·scorer/config를 검증·한국어 커밋·푸시해 실행 신원을 고정한다.
2. 다운로드·최대 192요청 범위를 확인한 뒤, `SYSTEM_CONTEXT_S4_DOWNLOAD=KANANA3B_PINNED_V1`과 `download --execute`로 위 revision만 수집한다. `.venv/bin/python -B -m scripts.evaluation.system_context_s4 verify-model`로 모든 로컬 파일을 다시 확인한다.
3. 오프라인 `execute`(인자 `--execute` 없이)로 실제 dry-run을 수행한다. 반환된 build·최대 입력·동일 의미·무삭제 조건을 확인하고 기존 local sysroot의 Python 3.10 헤더를 `CPATH`에 지정한다. native JIT는 끄지 않는다.
4. GPU·다른 세션·서비스를 다시 확인한 뒤 `SYSTEM_CONTEXT_S4=K0_KANANA3B_P0_V1`과 오프라인 환경에서 `execute --execute --build <확인한-build>`로 단일 실험을 진행한다. 같은 신원의 정상 중단만 `--resume`으로 재개하며 불확실한 시작·오류 요청은 재생성하지 않는다.
5. 별도 `verify --build <동일-build>`로 결과를 재구성한다. 조건별 분모·비용·판정 불가·대응쌍·검사 한계를 분석한 뒤에만 Phase 9의 실제 비교 완료 여부를 기록한다. 결과가 나쁘거나 자원이 부족해도 학습·다른 모델·운영 변경을 자동 실행하지 않는다.
